continnumOS — dissecacao didatica do codigo

Este documento abre o capo do sistema e explica, de forma progressiva e didatica, o que cada arquivo faz, como as funcoes trabalham linha a linha e como as pecas se conectam para formar um CRM/atendimento WhatsApp multi-tenant com IA.

~290 rotas HTTP/WS
~330 funcoes
12 loops de fundo
Fases 0-13 entregues
Como este guia foi montado Os modulos menores e centrais (autenticacao, multi-tenancy, motores de IA e de fluxos) sao explicados linha a linha. Os dois arquivos gigantes — main.py (7.043 linhas) e database.py (5.036 linhas) — sao dissecados por blocos logicos, com as funcoes-chave anotadas linha a linha e um mapa completo de todas as rotas e funcoes. Assim voce entende cada peca sem precisar rolar 10 mil linhas de uma vez.

Como ler

  • Blocos com fundo escuro e borda laranja sao codigo real do sistema.
  • As tabelas de duas colunas mostram codigo → explicacao linha a linha.
  • Caixas laranja trazem conceitos; caixas vermelhas trazem alertas; caixas verdes trazem boas praticas.
  • Use o filtro na barra lateral para achar uma secao rapidamente.

1. Arquitetura geral

O continnumOS e uma aplicacao FastAPI (Python assincrono) que serve um painel web e recebe eventos do WhatsApp via Evolution API. Os dados ficam em PostgreSQL (via asyncpg) com isolamento por tenant usando Row-Level Security. O Redis cuida de tempo real (pub/sub de WebSocket), travas, rate-limit, agendamentos e fila de jobs.

2. O ciclo de vida de uma requisicao (multi-tenant + RLS)

Este e o conceito mais importante do sistema. Cada requisicao web descobre qual empresa (tenant) esta falando e, a partir dai, o banco so devolve dados daquela empresa — automaticamente. Entender isso e a chave para entender todo o resto.

1. Chega uma requisicao no main.py (ex.: GET /painel) 2. A rota depende de get_current_user() (auth.py) 3. get_current_user chama db.resolve_request_tenant_id(request) -> descobre o tenant pelo dominio/host ou instancia 4. set_current_tenant(tenant_id) grava o id num contextvar (tenant_context.py) 5. load_tenant_config(tenant_id) aquece marca/horario no cache (tenant_config.py) 6. Qualquer query usa o pool asyncpg; ao pegar conexao, o hook _apply_tenant_guc roda SET app.current_tenant = <id> 7. O PostgreSQL aplica as policies de Row-Level Security: as tabelas so retornam linhas WHERE tenant_id = app.current_tenant 8. A rota devolve so os dados do tenant certo, sem filtrar manualmente.
Por que isso e genial Em vez de lembrar de escrever WHERE tenant_id = X em centenas de queries (e arriscar vazar dados entre clientes se esquecer uma), o isolamento e feito uma vez no nivel do banco. O codigo de aplicacao fica limpo e o vazamento entre tenants fica praticamente impossivel.

3. config.py — configuracao e segredos 230 linhas

Le variaveis de ambiente e falha no boot se um segredo obrigatorio faltar (principio "fail-fast"). Centraliza tudo numa classe Config exposta como settings.

3.1 Leitores de ambiente (linha a linha)

class ConfigError(RuntimeError): ...
Erro proprio para problemas de configuracao — deixa claro nos logs que a falha e de setup, nao de codigo.
def env_bool(name, default=False):
Le uma env e interpreta "1/true/yes/on" como verdadeiro. Usado por dezenas de flags (rate-limit, jobs, metrics...).
def env_str(name, default=None, required=False):
Le texto. Se required=True e a env estiver vazia, lanca ConfigError — o app nem sobe.
def env_list(name, default=""):
Le uma lista separada por virgula (ex.: ALLOWED_ORIGINS).
def _read_secret_file(path): ...
Le um segredo de um arquivo (padrao Docker/Kubernetes "secrets"), em vez de env em texto plano.
def env_secret(name, default=None, required=False):
Tenta primeiro NAME_FILE (arquivo de segredo); se nao houver, cai na env comum. Base da "rotacao/gestao de segredos" da Fase 6.

4. auth.py — autenticacao 142 linhas

Cuida de quem esta logado. Senhas sao verificadas com bcrypt; a sessao vira um cookie JWT assinado; e (opcionalmente) o Redis garante uma sessao ativa por usuario.

4.1 verify_user — validar login e senha

async def verify_user(username, password):
    users = await db.get_all_system_users()
    for user in users:
        if user['username'].lower() == username.lower() and user['is_active']:
            if bcrypt.checkpw(password.encode(), user['password'].encode()):
                return user
    return None
users = await db.get_all_system_users()
Busca os usuarios do tenant atual (o RLS ja restringe). Chamada dentro do contexto de tenant resolvido antes.
if ... and user['is_active']:
So aceita usuario ativo. Comparacao de nome e case-insensitive.
bcrypt.checkpw(...)
Compara a senha digitada com o hash bcrypt salvo. Nunca guarda senha em texto puro.

4.2 O cookie de sessao (JWT)

create_access_token(data)
Monta o JWT com exp = agora + SESSION_TTL_SECONDS e assina com JWT_SECRET. Vira o cookie session_token.
register_login_session(username, role)
Se ENFORCE_SINGLE_SESSION estiver ligado (e nao for admin), grava um jti no Redis com nx=True: se ja existir sessao, recusa o novo login.
validate_login_session(...)
A cada requisicao, confere se o jti do cookie bate com o do Redis; se nao, a sessao foi "roubada"/expirada em outro lugar.
clear_login_session / clear_session_from_request
Logout: apaga a trava do Redis (so quando a sessao unica esta ativa).

4.3 get_current_user — o portao de entrada de quase toda rota

Quase toda rota declara user: dict = Depends(get_current_user). Alem de autenticar, esta funcao ativa o tenant da requisicao. E o ponto onde autenticacao e multi-tenancy se encontram.

tenant_id = await db.resolve_request_tenant_id(request)
Descobre o tenant pelo host/dominio ou instancia da requisicao.
set_current_tenant(tenant_id)
Grava no contextvar — a partir daqui, toda query fica isolada nesse tenant (RLS).
await load_tenant_config(tenant_id)
Aquece o cache de marca/horario para leitura sincrona nos handlers.
if await db.get_tenant_status(tenant_id) != "active": return None
Bloqueia tenants suspensos (inadimplencia) — ninguem entra no painel.
token = request.cookies.get("session_token")
Pega o cookie de sessao; sem ele, retorna None (nao logado).
payload = jwt.decode(token, SECRET_KEY, ...)
Valida a assinatura e a expiracao do JWT. Excecoes especificas tratam token expirado e invalido.
for user in users: if match and is_active: validate_login_session(...); return user
Confirma que o usuario do token existe, esta ativo e que a sessao unica confere. So entao devolve o usuario.
Ponto sensivel Se get_current_user retornar None, as rotas respondem 401/redirect. Como ela tambem resolve o tenant, um bug aqui afeta tudo. Por isso ela e curta, defensiva e cheia de try/except.

5. tenant_context.py — o coracao do RLS 39 linhas

Arquivo minusculo, importancia enorme. Ele guarda "qual tenant estou atendendo agora" de um jeito que funciona com codigo assincrono (varias requisicoes ao mesmo tempo, sem se misturarem).

import contextvars
Usa context variables: cada task assincrona (cada requisicao) enxerga o seu proprio valor, sem vazar para as outras. E como uma "variavel global segura por requisicao".
DEFAULT_TENANT_ID = 1
Tenant padrao = continnumOS. Os dados legados (antes do multi-tenant) foram migrados para o tenant 1.
_current_tenant_id = ContextVar("...", default=DEFAULT_TENANT_ID)
A variavel de contexto em si. Comeca no tenant padrao ate alguem definir outro.
def set_current_tenant(tenant_id): ... return _current_tenant_id.set(tid)
Define o tenant da requisicao atual. Converte para int com seguranca (cai no padrao se vier lixo). Retorna um token para reverter depois.
def get_current_tenant() -> int
Lido em dezenas de funcoes do database.py para saber qual tenant filtrar. E o "quem sou eu agora".
def reset_current_tenant(token)
Restaura o valor anterior (ignora tokens invalidos). Usado para nao "sujar" o contexto entre tarefas.
Como conecta com o banco O valor guardado aqui e lido pelo hook _apply_tenant_guc do database.py toda vez que uma conexao e retirada do pool: ele executa SET app.current_tenant = <id>. As policies de RLS do PostgreSQL comparam tenant_id com esse valor. Ou seja: este arquivo de 39 linhas comanda o isolamento de todo o banco.

6. tenant_config.py — config e marca por tenant 156 linhas

Cada tenant pode ter nome, cor, logo, telefone do admin, horario comercial e textos do bot diferentes. Este modulo resolve isso a partir da coluna JSONB tenants.settings, com cache em memoria para permitir leitura sincrona rapida (importante porque funcoes como is_business_hours() sao chamadas em muitos lugares e nao podem virar async).

_default_config()
Os padroes (compativeis com o comportamento antigo hardcoded): nome continnumOS, cor #FF6600, horario 8h-18h com almoco 12h-13h, mapa papel→instancia, mensagem de bom dia.
_merge(base, override)
Faz um merge que tambem funde dicionarios de segundo nivel (ex.: business_hours), para o tenant sobrescrever so o que quiser.
get_cached_config(tenant_id)
Leitura sincrona do cache; se ainda nao aquecido, devolve os padroes. Nunca bloqueia.
async load_tenant_config(tenant_id, force=False)
Le do banco (get_tenant_record), mescla com os padroes e cacheia por 30s. Chamada no boot, no login e no webhook para "esquentar" o cache.
invalidate(tenant_id)
Limpa o cache quando o admin muda a config (para refletir na hora).
is_business_hours(now, tenant_id)
Converte a hora atual (fuso -03:00) em minutos e compara com a janela do tenant. Base das automacoes de "fora do horario".

Helpers sincronos que leem do cache: role_session_map(), departamentos(), admin_phone(), brand(), business_hours(), morning_followup_message(). O main.py importa este modulo como tc.

7. permissions.py — papeis e permissoes 84 linhas

Centraliza "quem pode fazer o que", evitando espalhar if role == 'admin' pelo codigo. Modelo aditivo: os papeis antigos continuam funcionando.

PERM_VIEW_CHATS = "chats:view" ... PERM_TAKEOVER = "chats:takeover"
Constantes de permissao. Use-as nos endpoints em vez de strings soltas — evita erros de digitacao.
ROLE_PERMISSIONS = { "admin": {"*"}, "manager": {...}, "vendas_1": _AGENT, ... }
O mapa papel→conjunto de permissoes. admin tem o curinga * (tudo). Vendedores herdam o conjunto _AGENT (ver/enviar/assumir).
permissions_for(role)
Retorna o conjunto do papel; papel desconhecido cai no padrao _AGENT; curinga vira "todas".
has_permission(role, permission) / user_has_permission(user, permission)
Checagem booleana. Admin sempre True. E a forma recomendada de proteger acoes finas.
list_roles()
Lista papeis + permissoes para telas de admin (rota /api/roles).

8. database.py — a camada de dados 3900 linhas · ~180 funcoes

E o "banco falando Python". Nenhuma outra parte do sistema escreve SQL cru; tudo passa por funcoes daqui. Vamos entender primeiro o mecanismo (pool + RLS) e depois os grupos de funcoes.

8.1 O pool asyncpg e o hook de RLS

async def _apply_tenant_guc(conn):
O elo do RLS. Roda toda vez que uma conexao e adquirida do pool. Executa SELECT set_config('app.current_tenant', <tenant>, false) lendo get_current_tenant().
init_db()
Cria o pool (asyncpg.create_pool) registrando _apply_tenant_guc no setup; roda migracao/criacao de tabelas; garante o admin. Chamado no lifespan e no worker.
resolve_request_tenant_id(request)
Descobre o tenant pelo host (dominio proprio do cliente) e/ou cabecalhos; usado por get_current_user.
_migrate_multitenant(db)
Migracao historica que adicionou tenant_id e as policies de RLS as tabelas legadas (Fase 1).
health_check() / close_db()
Ping do banco (usado em /health) e fechamento gracioso do pool.
Dois tipos de tabela Tabelas com RLS (users, messages, system_users, tags, bot_settings...) sao filtradas automaticamente pelo GUC. As tabelas novas das Fases 9/10 (flows, kb, ai_settings, routing...) sao "globais": carregam tenant_id e sao filtradas manualmente com get_current_tenant() em cada query. As duas abordagens convivem.

9. evolution_service.py — a ponte com o WhatsApp 446 linhas

Encapsula todas as chamadas HTTP a Evolution API (o gateway nao-oficial de WhatsApp). O main.py importa como evo e nunca fala HTTP direto com o WhatsApp — sempre via este modulo.

Padroniza o numero/JID (ex.: adiciona sufixo do WhatsApp) para as chamadas.
evolution_result(ok, response, error)
Padroniza o retorno de toda funcao: um dict com ok, corpo e erro — o chamador sempre sabe se deu certo.
async send_message(chat_id, text, session="vendas", quoted_id=None)
Envia texto. Opcionalmente cita outra mensagem (quoted_id). Usada por todo o envio manual e automatico.
send_media / send_reaction / edit_message / delete_message_for_everyone
Midia (base64), reacoes emoji, edicao e exclusao para todos — espelham as acoes do WhatsApp.
download_media(payload, session_id)
Baixa a midia que chegou num webhook e a entrega ao storage (S3/local).
get_connection_state / create_instance / ensure_instance / logout_instance
Gerenciam a "instancia" (conexao de um numero). ensure_instance cria se nao existir — base do onboarding de WhatsApp.
send_status(session, status_type, content, jid_list, ...)
Publica um "status" (story) para uma lista de contatos.

Como conecta Quando um atendente clica "enviar" no painel, a rota /api/chat/send chama evo.send_message(...) e depois db.save_message(...). Quando o cliente responde, o WhatsApp chama /webhook, que usa evo.download_media (se for midia) e grava com db.save_message. Este modulo e a fronteira entre "nosso sistema" e "o WhatsApp".

10. main.py — o servidor 6114 linhas · ~200 rotas

E o maestro. Ele monta o app FastAPI, aplica middlewares, sobe os loops de fundo, expoe todas as rotas do painel/API e — o mais importante — roda o pipeline do webhook que transforma cada mensagem recebida do WhatsApp em acao. Vamos por blocos.

No topo o arquivo define os modelos de entrada (validam o corpo dos POSTs) e funcoes utilitarias reaproveitadas em muitas rotas.

10.4 O pipeline do webhook — o coracao do atendimento

Toda mensagem do cliente entra por aqui. E a sequencia mais importante do sistema inteiro.

@app.post("/webhook")                      # l.4382
async def webhook(request: Request):
    data = await request.json()
    # valida o segredo, resolve tenant, e delega:
    return await process_webhook(data)   # l.4416

Dentro de process_webhook (dissecado em passos logicos):

1. valida WEBHOOK_SECRET + rate-limit do webhook
Rejeita chamadas nao assinadas e limita volume (protege custo/abuso — Fase 6).
2. resolve tenant + set_current_tenant(...)
Identifica de qual cliente e a instancia e ativa o RLS para o resto do processamento.
3. extrai evento/mensagem do payload da Evolution
Normaliza o formato (texto, midia, reacao, ack de entrega/leitura...).
4. db.claim_webhook_message(waha_id)
Idempotencia: se essa mensagem ja foi processada, para aqui — evita duplicar em reenvios/retries.
5. se for midia -> evo.download_media(...)
Baixa e guarda no storage; salva a referencia.
6. get_user()/create_user() + save_message()
Garante o contato e grava a mensagem recebida no historico.
7. detect_bot_loop_risk() / can_send_automated_reply()
Decide se pode responder automaticamente (anti-loop + horario + estagio).
8. apply_ai_pipeline(...) <- Fase 10
Roda IA sobre a mensagem (sentimento, score, sugestao) e guarda o resultado. Detalhado na secao 13.
9. run_active_flow(...) <- Fase 10
Se houver um fluxo no-code ativo para esse contato, avanca a maquina de estados e executa as acoes (enviar msg, aplicar tag, transferir).
10. logica de menu/atendimento (se nao em fluxo)
Trata escolha de setor, fila "pendente assumir", encaminhamento ao atendente, etc.
11. broadcast WebSocket p/ o painel
Empurra a nova mensagem em tempo real para a tela dos atendentes (via Redis pub/sub).
Ordem importa A IA (passo 8) roda depois das travas anti-loop (passo 7), e o fluxo (passo 9) roda antes da logica de menu antiga — e so para sessoes que nao sejam financeiro/engenharia e cujo estagio nao seja em_atendimento/carteira. Assim a automacao nova convive com o atendimento humano sem atropelar.

11.3 RAG — responder a partir da base de conhecimento

RAG ("geracao aumentada por recuperacao") deixa a IA responder com base nos documentos do cliente, nao no conhecimento generico do modelo.

12. flow_engine.py — o motor de fluxos no-code 232 linhas · Fase 10

Uma maquina de estados pura: dado o fluxo (desenhado pelo admin), o estado atual do contato e a mensagem que ele mandou, decide o proximo no e quais acoes executar. "Pura" = nao acessa banco nem rede; so calcula. Isso a torna testavel e previsivel.

12.1 Funcoes auxiliares

_norm(s)
Normaliza texto (minusculas, sem acento/espaco extra) para comparar opcoes com tolerancia.
render_vars(text, ctx)
Substitui variaveis no texto do no com dados do contato. Monta a marca com "{"+str(k)+"}" (evita o bug de chaves).
_match_option(text, options)
Casa a resposta do cliente com uma opcao do menu (por numero ou por texto aproximado).
_check_condition(cond, ctx)
Avalia condicoes de ramificacao (ex.: valor > 100, tag presente) para nos do tipo "condition".
new_state(flow)
Cria o estado inicial apontando para o no start do fluxo.

12.2 run() — o passo do fluxo

def run(flow, state, text, ctx):
    actions = []
    steps = 0
    node = flow["nodes"][state["current"]]
    while steps < MAX_STEPS:        # MAX_STEPS = 25 (anti-loop)
        steps += 1
        kind = node["type"]
        if kind == "message": actions.append(("send", render_vars(node["text"], ctx)))
        elif kind == "question": ... # envia e espera resposta (para o loop)
        elif kind == "condition": node = branch(...)
        elif kind == "action": actions.append((node["action"], node.get("value")))
        elif kind == "end": state["done"] = True; break
    return state, actions
while steps < MAX_STEPS
Trava anti-loop: no maximo 25 nos por passo. Fluxo mal desenhado nunca trava o processo.
kind == "message" -> actions.append(("send", ...))
Nos de mensagem nao enviam direto: geram uma acao "send". Quem envia de fato e o main.py (mantendo o motor puro).
kind == "question" -> para o loop
Ao chegar numa pergunta, envia e interrompe, salvando o estado para retomar quando o cliente responder.
kind == "condition" -> branch(...)
Escolhe o proximo no conforme _check_condition. Permite arvores de decisao.
kind == "action" -> (acao, valor)
Gera acoes como aplicar tag, transferir para setor, marcar lead — executadas pelo main.py.
return state, actions
Devolve o novo estado (para salvar) e a lista de acoes (para executar). Contrato simples e testavel.
validate_flow(flow)
Confere antes de salvar: existe no start? Todos os destinos existem? Sem isso o admin poderia salvar um fluxo quebrado.
Separacao de responsabilidades O motor decide (puro), o main.py executa (efeitos colaterais: enviar via evo, gravar via db). Esse desenho e o que permitiu o autoteste passar sem banco na validacao da Fase 10.

19. Fluxos ponta a ponta (juntando tudo)

19.1 Login

POST /login -> verify_user (bcrypt) -> create_access_token (JWT) -> register_login_session (Redis, se sessao unica) -> Set-Cookie session_token -> redireciona ao painel (admin ou vendas conforme o papel)

19.2 Atendente envia uma mensagem

painel -> POST /api/chat/send (Depends get_current_user: autentica + ativa tenant) -> evo.send_message(...) (Evolution) -> db.save_message(...) (RLS grava no tenant certo) -> broadcast WebSocket -> aparece na tela

19.3 Cliente responde (com IA + fluxo)

WhatsApp -> POST /webhook -> valida segredo + rate-limit -> resolve/ativa tenant -> claim_webhook_message (idempotencia) -> [midia? download] -> save_message -> anti-loop/horario OK? -> apply_ai_pipeline (sentimento/score) -> run_active_flow (flow_engine.run -> acoes: send/tag/transfer) -> ou logica de menu/fila -> broadcast WebSocket

19.4 Admin cria um fluxo no-code

ai_admin_js (formulario) -> POST /api/flows (valida com flow_engine.validate_flow) -> db salva o fluxo (tenant_id) -> simulador chama flow_engine.run em memoria -> ativado: o proximo cliente entra por run_active_flow no webhook

19.5 Inadimplencia suspende o tenant

billing_enforcement_loop -> mark_overdue_invoices -> passa grace period? -> set_tenant_status('suspended') -> get_current_user bloqueia login -> pagamento chega em /payment/webhook -> mark_invoice_paid -> reactivate_tenant_if_paid
