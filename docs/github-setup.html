continnumOS — deixando o repositório com cara de projeto profissional

Este guia mostra, passo a passo, como publicar o continnumOS no GitHub de forma organizada e profissional: descrição, topics, README com SVG e badges, imagem de social preview, arquivos de comunidade, proteção de branch, releases e a publicação do site via GitHub Pages.

O que ja vem pronto no projeto O repositório ja inclui README.md (com banner SVG e badges), CONTRIBUTING.md, SECURITY.md, LICENSE, .github/assets/banner.svg e o workflow de CI em .github/workflows/ci.yml. Este guia cobre o que se configura na interface do GitHub.

1. Higiene antes de subir

Nunca suba segredos Confirme que o .env real nao vai para o Git. O .gitignore ja ignora .env, __pycache__/, *.pyc, logs e arquivos .vcf. Suba apenas o .env.example.
# confira o que seria commitado (o .env NAO deve aparecer)
git status
git check-ignore .env      # deve imprimir: .env

# se um segredo ja foi commitado antes, rotacione-o e remova do historico
git rm --cached .env

2. Criar o repositório & primeiro push

1

Criar no GitHub

Crie um repo (ex.: continnumos). Deixe-o privado se o código for proprietário (recomendado).
2

Enviar o código

git init
git add .
git commit -m "chore: primeiro commit do continnumOS"
git branch -M main
git remote add origin https://github.com/OWNER/REPO.git
git push -u origin main
Troque OWNER/REPO pelo seu usuário/organização e nome do repo.

4. README que aparece na home & badges

O README.md já renderiza automaticamente na home do repo, com o banner SVG no topo. Os badges usam o shields.io. O badge de CI precisa apontar para o seu repo:

# adicione no topo do README (troque OWNER/REPO)
![CI](https://github.com/OWNER/REPO/actions/workflows/ci.yml/badge.svg)
Dica de leitura Um bom README responde em 30 segundos: o que é, como rodar e onde está a documentação. O README incluído já segue essa ordem (visão geral → recursos → arquitetura → começando → docs).

5. Social preview (a imagem que aparece ao compartilhar)

O social preview é a imagem exibida quando o link do repo é compartilhado (WhatsApp, X, Slack...). Configure em Settings → General → Social preview.

1

Gerar um PNG a partir do banner

O GitHub aceita PNG/JPG (1280×640 recomendado). Converta o .github/assets/banner.svg: 
# com ImageMagick ou rsvg-convert
rsvg-convert -w 1280 -h 640 .github/assets/banner.svg -o social-preview.png
2

Enviar

Em Settings → Social preview, faça upload do PNG. Pronto — o repo passa a ter uma vitrine com a sua marca.

7. Proteção de branch & CI

Em Settings → Branches → Add rule, proteja a main:

  • Exigir Pull Request antes de merge.
  • Exigir que os checks de status passem (selecione o job build-test do CI).
  • Exigir branch atualizada e, se possível, revisão de 1 aprovador.
CI ja configurado O workflow .github/workflows/ci.yml sobe PostgreSQL e Redis reais e roda os testes (incluindo isolamento RLS entre tenants) a cada push/PR. Com a proteção de branch, nada entra na main sem o CI verde.

8. Releases, tags & CHANGELOG

O projeto já mantém um CHANGELOG_SAAS.md por fases. Transforme marcos em Releases:

git tag -a v1.0.0 -m "Fases 0-13 completas"
git push origin v1.0.0

Depois, em Releases → Draft a new release, escolha a tag, cole as notas da fase e publique. Isso cria a seção "Releases" na home e um histórico versão a versão.

9. Publicar o site com GitHub Pages (pasta site/)

O guia de deploy foi publicado dentro do site (site/deploy.html). Você pode servir a pasta site/ gratuitamente pelo GitHub Pages.

1

Ativar

Em Settings → Pages, em "Build and deployment", escolha Deploy from a branch, selecione main e a pasta /site (ou /root se mover os arquivos). Salve.
2

Acessar

Em instantes o site fica em https://OWNER.github.io/REPO/. A landing (index.html), a documentação (docs.html) e o guia de deploy (deploy.html) ficam públicos.
Mantenha a dissecacao interna A dissecacao didática do código fica em docs/ (interna ao repo) e nao no site/. Assim ela nao é publicada pelo Pages — ela expõe a arquitetura interna e deve permanecer restrita.

10. Organização & vitrine do perfil

  • Pins: fixe o repositório no seu perfil/organização ("Customize your pins").
  • Labels: padronize labels (bug, feature, docs, good first issue).
  • Milestones/Projects: use o roadmap por fases como marcos ou um quadro de projeto.
  • Perfil README: um repo OWNER/OWNER com README aparece no topo do seu perfil — ótimo para apresentar o continnumOS.
