continnumOS — instalacao do ambiente, do zero ao primeiro acesso

Este guia leva voce, passo a passo, de um servidor vazio ate o painel do continnumOS aberto no navegador e o WhatsApp conectado. Tudo com Docker, o arquivo .env e comandos prontos para copiar.

4 containers
1 arquivo .env
~15 min instalacao
Docker Compose
Postgres 15 + Redis
O que voce vai precisar em maos Um servidor Linux com acesso root/sudo, um dominio (opcional, mas recomendado para HTTPS) e ~15 minutos. Nao e preciso instalar Python, Postgres ou Redis manualmente — o Docker cuida de tudo.

Como ler

  • Blocos escuros com borda laranja sao comandos ou arquivos reais — copie e cole.
  • obrigatorio voce precisa preencher. seguranca troque antes de ir a producao. opcional pode deixar o padrao.
  • Caixas azuis trazem dicas, verdes boas praticas, vermelhas alertas.

1. Arquitetura do deploy

O sistema sobe como 4 containers orquestrados por um unico docker-compose.yaml. Eles conversam por uma rede interna do Docker (referenciando-se pelo nome do servico).

INTERNET | (porta 8000 -> painel / 8080 -> Evolution) +-----------------+------------------+ | | bot (FastAPI) <--- webhook --- evolution_api (WhatsApp) porta 8000 porta 8080 | \ | | \____________ _____________________| v v v postgres_db (15) redis (tempo real/travas/filas) volume pg_data (pub/sub, rate-limit, agendamentos)
ContainerImagemPapelPorta
botbuild local (Dockerfile)A aplicacao: painel web, API e webhook. E o continnumOS em si.8000
evolution_apievoapicloud/evolution-apiGateway do WhatsApp: conecta o numero e entrega mensagens ao bot via webhook.8080
postgres_dbpostgres:15-alpineBanco de dados (com isolamento por tenant via RLS). Dados persistem no volume pg_data.interna
redisredis:alpineTempo real (WebSocket pub/sub), travas, rate-limit, agendamentos e fila de jobs.interna
Por que so o painel e o Evolution expoem porta Apenas bot (8000) e evolution_api (8080) publicam portas. Postgres e Redis ficam fechados na rede interna — nao sao acessiveis de fora, o que e mais seguro.

2. Pre-requisitos

2.1 Servidor

  • SO: Ubuntu 22.04+ (ou qualquer Linux com Docker).
  • Recursos minimos: 2 vCPU e 4 GB de RAM (os limites de memoria ja vem definidos no compose: bot 768m, postgres 768m, evolution 1024m, redis 256m).
  • Disco: 20 GB+ (banco, midias e backups crescem com o uso).

2.2 Instalar Docker + Compose

# Ubuntu/Debian - instalacao oficial do Docker Engine + plugin Compose
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER   # usar docker sem sudo (relogar depois)
docker --version
docker compose version

2.3 Dominio e DNS (recomendado)

  • Aponte um registro A do seu dominio (ex.: painel.seudominio.com) para o IP do servidor.
  • Para signup self-service com subdominio por cliente (Fase 8), crie tambem um wildcard *.seudominio.com apontando para o mesmo IP.

Toda a configuracao vive em um unico arquivo .env. Comece copiando o modelo:

cp .env.example .env

Antes de qualquer coisa Troque todos os valores que comecam com troque-.... Gere segredos fortes com o comando abaixo — nunca use os exemplos em producao.
# gera um segredo aleatorio forte (use um para cada *_SECRET / senha)

5. Docker explicado

5.1 O Dockerfile (imagem do bot)

FROM python:3.11-slim              # base enxuta
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN mkdir -p /data/midias /data/backups /app/logs   # dados/logs/backups
HEALTHCHECK ... CMD (consulta /health)     # reinicia se cair
CMD ["uvicorn","main:app","--host","0.0.0.0","--port","8000"]

Pontos importantes: instala as dependencias do requirements.txt, cria os diretorios de dados e define um healthcheck que consulta /health — se o app travar, o orquestrador reinicia o container.

5.2 O docker-compose.yaml (os 4 servicos)

Ele define bot, evolution_api, postgres_db e redis, todos com restart: always e limites de memoria. Detalhes que valem entender:

  • O bot carrega o .env via env_file e monta volumes (bot_data para /data, alem de static, templates, logs).
  • O evolution_api ja vem configurado para enviar eventos ao http://bot:8000/webhook com o cabecalho Bearer WEBHOOK_SECRET — a integracao com o WhatsApp e automatica.
  • depends_on garante a ordem de subida (banco/redis/evolution antes do bot).
  • Persistencia: volumes pg_data (banco) e bot_data (midias/backups). Nao apague esses volumes sem backup.
Workers no compose No compose o bot sobe com --workers 4. Se usar varios workers/replicas, deixe RUN_BACKGROUND_JOBS=true em apenas um processo para os loops de fundo (SLA, cadencias, follow-ups) nao duplicarem trabalho.

6. Subir o stack

1

Construir e iniciar

docker compose up -d --build
Sobe os 4 containers em segundo plano. Na primeira vez, o build da imagem do bot leva alguns minutos.
2

Conferir se estao de pe

docker compose ps          # todos 'running' / healthy
docker compose logs -f bot  # acompanhar o boot do app
Procure no log do bot pelas mensagens de criacao de tabelas (Fases 9 a 13) e "Application startup complete".
3

Testar a saude

curl http://localhost:8000/health   # deve responder OK/200
O que acontece no primeiro boot O app roda init_db() (cria o pool com RLS e todas as tabelas), garante o usuario admin a partir do .env, aquece o cache do tenant padrao e inicia os 12 loops de fundo (se RUN_BACKGROUND_JOBS=true).

7. Migrations versionadas (Alembic) producao

Para desenvolvimento, RUN_DB_MIGRATIONS_ON_BOOT=true cria as tabelas sozinho. Em producao seria, o recomendado e desligar isso e controlar o schema com Alembic (reproduzivel e reversivel):

# no .env
RUN_DB_MIGRATIONS_ON_BOOT=false

# aplicar as migrations (dentro do container bot)
docker compose exec bot alembic upgrade head

# criar uma nova migration apos mudar o schema
docker compose exec bot alembic revision --autogenerate -m "descricao"
Regra pratica Dev/homolog: boot cria tabelas (rapido). Producao: false + alembic upgrade head no deploy — assim toda mudanca de banco fica versionada e reversivel.

8. Primeiro acesso ao sistema

1

Abrir o painel

Acesse http://SEU_IP:8000 (ou https://painel.seudominio.com apos configurar o proxy).
2

Fazer login como admin

Use ADMIN_USERNAME e ADMIN_PASSWORD definidos no .env. O sistema cria esse usuario no primeiro boot e redireciona para o painel conforme o papel.
3

Trocar a senha e criar a equipe

Troque a senha do admin, e em Admin -> Usuarios cadastre os atendentes (papeis vendas_1, vendas_2, financeiro, engenharia).
Seguranca no primeiro dia Troque a senha do admin imediatamente, confirme que COOKIE_SECURE=true e que o painel so responde por HTTPS antes de expor a internet.

9. Conectar o WhatsApp (Evolution API)

O evolution_api ja sobe integrado ao bot. Falta apenas criar a instancia e parear o numero pelo QR Code.

1

Provisionar a instancia

No painel admin, em Instancias, crie/provisione uma instancia. Por baixo, o sistema chama o Evolution (ensure_instance) usando a EVO_API_KEY.
2

Ler o QR Code

Abra o WhatsApp -> Aparelhos conectados -> Conectar um aparelho no celular e escaneie o QR exibido no painel.
3

Validar a conexao

O estado deve ir para open/conectado. Envie uma mensagem de teste ao numero — ela deve aparecer no painel em tempo real (via webhook + WebSocket).
Como o webhook chega ate voce O Evolution esta configurado com WEBHOOK_GLOBAL_URL=http://bot:8000/webhook e Authorization: Bearer WEBHOOK_SECRET. Toda mensagem recebida entra pelo pipeline do webhook (idempotencia, IA, fluxos, roteamento) e e empurrada ao painel.

11. HTTPS e proxy reverso

Nao exponha a porta 8000 diretamente. Coloque um proxy reverso na frente para TLS/HTTPS. Exemplo com Caddy (HTTPS automatico via Let's Encrypt):

# Caddyfile
painel.seudominio.com {
    reverse_proxy localhost:8000
}

Ou com Nginx (trecho essencial):

server {
    server_name painel.seudominio.com;
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;      # WebSocket
        proxy_set_header Connection "upgrade";        # tempo real
    }
}
Nao esqueca o WebSocket O painel usa WebSocket (/ws) para tempo real. O proxy precisa repassar os cabecalhos Upgrade/Connection, senao a tela nao atualiza sozinha.

Depois do HTTPS, atualize ALLOWED_ORIGINS e mantenha COOKIE_SECURE=true.

11.1 Publicar o site institucional (site/)

O projeto inclui um site publico estatico em site/ — a landing (index.html), a documentacao (docs.html) e o tema (assets/site.css). Ele nao faz parte do container do app: o compose monta apenas static/ e templates/. Publique o site separadamente — pelo proxy reverso, por um host estatico ou CDN.

Arquitetura de dominios recomendada:

seudominio.com -> site/ (landing + docs, estatico) painel.seudominio.com -> bot:8000 (o app / console)

Opcao A — servir com Caddy (mesmo servidor)

# Caddyfile
seudominio.com {
    root * /opt/continnumos/site
    file_server
}
painel.seudominio.com {
    reverse_proxy localhost:8000
}

Opcao B — servir com Nginx

server {
    server_name seudominio.com;
    root /opt/continnumos/site;
    index index.html;
    location / { try_files $uri $uri/ =404; }
}
Sem build, sem dependencias O site e HTML/CSS puro (icones via sprite SVG inline). Basta publicar a pasta site/ — nenhum passo de compilacao. Os botoes "Documentacao" e "Comecar" ja apontam para docs.html e para as ancoras de planos; ajuste os links para o dominio do seu painel (ex.: https://painel.seudominio.com/login) se quiser levar direto ao acesso.

12. Segredos em producao

Deixar segredos em .env plano e aceitavel para comecar, mas em producao prefira arquivos de segredo (Docker/K8s secrets). O sistema resolve cada segredo nesta ordem de precedencia:

{NOME}_FILE  >  SECRETS_DIR/{NOME}  >  variavel de ambiente
# exemplos
JWT_SECRET_FILE=/run/secrets/jwt_secret
# ou aponte um diretorio com um arquivo por segredo:
SECRETS_DIR=/run/secrets
Boa pratica Rotacione JWT_SECRET, WEBHOOK_SECRET, senhas do banco e chaves de pagamento periodicamente. Nunca versione o .env no Git — o .dockerignore ja ajuda a nao vaza-lo na imagem.

13. Backups e restore (DR)

13.1 Backup do banco

# dump logico do Postgres (rode via cron diariamente)
docker compose exec -T postgres_db pg_dump -U $POSTGRES_USER $POSTGRES_DB \
  > backup_$(date +%F).sql

13.2 Backup de midias/dados

# o volume bot_data guarda /data (midias, backups)
docker run --rm -v continnumos_bot_data:/data -v $PWD:/out alpine \
  tar czf /out/bot_data_$(date +%F).tgz /data

13.3 Restore (teste periodicamente!)

cat backup_2026-07-05.sql | docker compose exec -T postgres_db \
  psql -U $POSTGRES_USER $POSTGRES_DB
Backup nao testado nao existe Restaure em um ambiente separado de tempos em tempos para garantir que o processo funciona de verdade. Documente o RTO/RPO da sua operacao.

16. Troubleshooting

SintomaCausa provavel / solucao
Bot reinicia em loopHealthcheck falhando. Veja docker compose logs bot: geralmente DATABASE_URL errado ou Postgres ainda subindo.
"password authentication failed"DATABASE_URL nao bate com POSTGRES_PASSWORD. Alinhe os dois e recrie: docker compose up -d.
WhatsApp nao entrega mensagensWEBHOOK_SECRET diferente entre bot e Evolution, ou a instancia nao esta open. Reescaneie o QR.
Painel nao atualiza em tempo realProxy sem repasse de WebSocket (Upgrade/Connection). Ajuste o Nginx/Caddy.
Login cai / cookie nao ficaCOOKIE_SECURE=true sem HTTPS. Ative o TLS ou (so em teste) use false.
Erro de CORSOrigem ausente em ALLOWED_ORIGINS. Inclua a URL do painel.
Loops rodando 2xMais de um processo com RUN_BACKGROUND_JOBS=true. Deixe em apenas um.
